# Квитто — API платежей: требования

Сервис, через который онлайн-школа принимает оплату курса: тарифы, создание платежа, просмотр платежей, вебхук банка о смене статуса.

---

## 1. Стек

| Компонент | Выбор |
|---|---|
| Язык | Python 3.11+ |
| Фреймворк | FastAPI, Pydantic v2 |
| БД | PostgreSQL |
| ORM | SQLAlchemy 2.x |
| Миграции | Alembic |
| Тесты | pytest + httpx |
| Запуск | `docker compose up` |

---

## 2. Сущности

### 2.1 Tariff — тариф

| Поле | Тип | Описание |
|---|---|---|
| `id` | `str` (PK) | Код тарифа: `basic`, `standard`, `premium` |
| `title` | `str` | Название |
| `price` | `int` | Цена в копейках |

Тарифы **создаются при старте приложения** (идемпотентный seed — повторный старт не создаёт дублей):

| id | Цена, ₽ | price, коп. |
|---|---|---|
| `basic` | 9 900 | `990000` |
| `standard` | 19 900 | `1990000` |
| `premium` | 29 900 | `2990000` |

### 2.2 Payment — платёж

| Поле | Тип | В ответе | Описание |
|---|---|---|---|
| `id` | `UUID` (PK) | да | Идентификатор платежа |
| `status` | `PaymentStatus` | да | Начальное значение — `pending` |
| `tariff_id` | `str` (FK → tariffs) | да | Оплачиваемый тариф |
| `amount` | `int` | да | Сумма к оплате в копейках (цена − скидка) |
| `discount` | `int` | да | Скидка в копейках, `0` без промокода |
| `method` | `PaymentMethod` | да | Способ оплаты |
| `installment_months` | `int \| null` | да | 3 / 6 / 12, только для `installment` |
| `schedule` | `list[int] \| null` | да | График рассрочки в копейках; `null`, если не рассрочка |
| `email` | `str` | да | Email плательщика |
| `created_at` | `datetime` (UTC, tz-aware) | да | Время создания |
| `promo_code` | `str \| null` | нет | Применённый промокод (история, аудит) |
| `idempotency_key` | `str \| null`, UNIQUE | нет | Значение заголовка `Idempotency-Key` |

### 2.3 Перечисления

- **PaymentMethod:** `card`, `sbp`, `installment`
- **PaymentStatus:** `pending`, `succeeded`, `failed`, `refunded`
- **InstallmentMonths:** `3`, `6`, `12`

### 2.4 Промокоды

Таблицы нет: у промокода нет собственного состояния (срока, лимита, активности). Справочник в коде и одна функция поиска:

```python
PROMO_CODES: dict[str, int] = {"KVITTO10": 10}  # код → процент скидки

def get_discount_percent(code: str) -> int:
    try:
        return PROMO_CODES[code.strip().upper()]
    except KeyError:
        raise UnknownPromoCode(code)
```

Если появится состояние (срок действия, лимит использований, привязка к тарифам), справочник переезжает в таблицу. Меняется только тело `get_discount_percent`, сервис платежей не затрагивается.

## 3. Бизнес-правила

### 3.1 Деньги
- Все суммы в API и в БД — **целое число копеек**. Никаких `float` и `Decimal` в хранении.
- В БД — `BigInteger`.
- Скидка считается целочисленно: `discount = price * percent // 100` (округление вниз).
- `amount = price - discount`.

### 3.2 Промокод
- Необязательное поле. Пустая строка считается отсутствием промокода.
- Сравнение без учёта регистра и пробелов по краям.
- Неизвестный код → **422**.

### 3.3 Рассрочка
- Для `method = installment` поле `installment_months` **обязательно**, допустимые значения 3, 6, 12.
- Для `card` / `sbp` передача `installment_months` → **422**; `installment_months` и `schedule` в ответе — `null`.
- Алгоритм графика:
  ```python
  base, rest = divmod(amount, months)
  schedule = [base + 1] * rest + [base] * (months - rest)
  ```
- Инвариант: `sum(schedule) == amount`, лишние копейки — в первые платежи. Даты платежей не нужны.
- Пример: `standard`, без промокода, 3 мес. → `amount = 1990000`, `schedule = [663334, 663333, 663333]`.

### 3.4 Статусы

Допустимые переходы (все остальные запрещены, включая переход в тот же статус):

```
pending   → succeeded
pending   → failed
succeeded → refunded
```

`failed` и `refunded` — конечные статусы.

### 3.5 Идемпотентность создания
- Заголовок `Idempotency-Key` необязателен.
- Без заголовка каждый запрос создаёт новый платёж (201).
- С заголовком, если платёж с таким ключом уже есть, вернуть **его же** с кодом **200**, второй не создавать. Тело повторного запроса не сравнивается.
- Защита от гонки: UNIQUE-индекс на `idempotency_key`; при `IntegrityError` перечитать и вернуть существующий платёж.

## 4. Эндпоинты

### 4.1 `GET /tariffs`
- **200** — `[{ "id", "title", "price" }]`.

### 4.2 `POST /payments`

Тело:
```json
{
  "tariff_id": "standard",
  "email": "user@example.com",
  "method": "installment",
  "installment_months": 3,
  "promo_code": "kvitto10"
}
```

Заголовок (необязательный): `Idempotency-Key: <string>`

| Ситуация | Код |
|---|---|
| Платёж создан | **201** + платёж |
| Ключ уже использован | **200** + существующий платёж |
| Невалидное тело / email / method / months | **422** |
| `installment` без `installment_months` | **422** |
| `installment_months` при `card` / `sbp` | **422** |
| Неизвестный промокод | **422** |
| Неизвестный тариф | **422** |

### 4.3 `GET /payments/{id}`
- **200** — платёж.
- **404** — платежа нет.
- **422** — `id` не является UUID.

### 4.4 `GET /payments`
- Query-параметры (оба необязательные, комбинируются через AND): `email`, `status`.
- **200** — список платежей, сортировка по `created_at` по убыванию.
- **422** — неизвестный `status`.

### 4.5 `POST /webhooks/bank`

Тело: `{ "payment_id": "<uuid>", "status": "succeeded" }`

| Ситуация | Код | Ответ |
|---|---|---|
| Успешный переход | **200** | `{ "result": "ok" }` |
| Платежа нет | **404** | стандартный |
| Запрещённый переход (в т.ч. повтор того же статуса) | **409** | `{ "error": "invalid_transition" }`, статус не меняется |
| Невалидное тело / неизвестный статус | **422** | стандартный |

Смена статуса атомарная: `SELECT … FOR UPDATE`, чтобы параллельные вебхуки не обошли проверку перехода.

### 4.6 Формат платежа в ответах

```json
{
  "id": "6f1c…",
  "status": "pending",
  "tariff_id": "standard",
  "amount": 1990000,
  "discount": 0,
  "method": "installment",
  "installment_months": 3,
  "schedule": [663334, 663333, 663333],
  "email": "user@example.com",
  "created_at": "2026-10-09T13:04:00Z"
}
```

### 4.7 Ошибки
- Ошибки валидации — стандартный ответ FastAPI **422** `{"detail": [...]}`.
- Бизнес-ошибки валидации (промокод, тариф) — тоже 422 в формате, совместимом с FastAPI.
- Единственный кастомный формат — 409 `{"error": "invalid_transition"}`.

---

## 5. Инфраструктура

- **Docker Compose:** сервисы `app` и `db` (PostgreSQL) с healthcheck; `app` стартует после готовности `db`, применяет миграции и seed тарифов.
- **Alembic:** начальная миграция с таблицами `tariffs` и `payments`.
- **Тестовая БД:** отдельная база PostgreSQL, схема пересоздаётся на сессию pytest. SQLite не используется: тесты должны проверять поведение той же СУБД (блокировки, `timestamptz`).

---

## 6. Тесты (pytest + httpx)

Тесты проверяют **результат** (суммы, статус в БД, количество записей), а не только код ответа.

**Обязательные:**
1. Сумма без промокода и с промокодом, в т.ч. промокод в нижнем регистре (`kvitto10`).
2. График рассрочки: `sum(schedule) == amount` для 3, 6 и 12 месяцев; лишние копейки в начале.
3. Повтор с тем же `Idempotency-Key` → 200, тот же `id`, в БД один платёж.
4. Запрещённый переход → 409, `{"error": "invalid_transition"}`, статус после повторного `GET` не изменился.
5. Несуществующий платёж → 404.

**Дополнительные:**
- Неизвестный промокод → 422.
- `installment` без `installment_months` и с недопустимым значением → 422.
- `GET /tariffs` возвращает 3 тарифа с ценами в копейках.
- Разрешённые переходы статусов → 200, статус обновлён.
- Вебхук на несуществующий платёж → 404.
- `GET /payments` с фильтрами по `email` и `status`.
- Юнит-тесты функций расчёта скидки и графика.
